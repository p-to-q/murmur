# Packaging and Release

This document explains the recommended path from a private GitHub repository to
validated builds and user-facing deliverables.

It is intentionally practical: start with private collaboration, validate in CI,
produce build artifacts, then publish only the surfaces that need to be public.

## Current facts

### Repository collaboration

Murmur can be developed in a private GitHub repository without issue. GitHub
also supports sharing reusable Actions and workflows across private repositories
inside an organization, with explicit access settings in repository Actions
configuration. Source: [GitHub Docs: Sharing actions and workflows with your organization](https://docs.github.com/actions/sharing-automations/sharing-actions-and-workflows-with-your-organization)

### Release artifacts

GitHub Releases can attach distributable assets in addition to the auto-generated
zip and tarball of the repository at a tag. Source: [GitHub Docs: About releases](https://docs.github.com/articles/about-releases?ref=amos-blog)

### Current Vercel constraint

This repository currently cannot rely on Vercel Hobby deployment from a private
GitHub organization repository. The existing check failure states that private
organization repository deploys require a Pro plan. That is consistent with the
Vercel deployment restriction already surfaced in PR checks.

### Prebuilt deploy option

If Vercel remains the host, Vercel supports `vercel build` followed by
`vercel deploy --prebuilt`, which lets a prebuilt project be deployed without
sharing source code with Vercel at deploy time. Source:

- [Vercel CLI: vercel build](https://vercel.com/docs/cli/build)
- [Vercel CLI: vercel deploy](https://vercel.com/docs/cli/deploy)

## Recommended delivery model

For Murmur, use three distinct outputs:

1. **Source collaboration output**
   Private GitHub repository, issues, PRs, docs, review history.
2. **Engineering build output**
   Verified app build artifacts and CI receipts.
3. **User-facing product output**
   Deployed app plus exported assets generated by Murmur itself.

Do not mix these together.

## Release types

Murmur should treat two release types as first-class:

### 1. Product release

A product release means the hosted web app is stable enough for active use or
review.

Required signals:

- deploy target is known
- `lint` and `build` are green
- critical user flow is manually checked
- environment contract is current

### 2. Artifact release

An artifact release means Murmur's export surfaces are stable enough to be
treated as part of the product contract.

Current artifact surfaces:

- MP3
- WAV fallback
- poster PNG
- share HTML
- video export (MP4 or WebM, browser-dependent)

Required signals:

- export surfaces still generate successfully
- output behavior matches current product expectations
- known limitations are documented if any export remains browser-dependent

## Recommended private-repo workflow

### Stage 1. Private collaboration

Use the private repository for:

- source code
- issues and PRs
- architecture and workflow docs
- internal demo discussion

Recommended default:

- feature branches
- PR-based merge to `main`
- explicit validation in PR body

## Stage 2. Validation and packaging

On every release-candidate merge or tag:

1. run `bun install`
2. run `bun run lint`
3. run `bun run build`
4. optionally run smoke checks against localhost or preview deployment
5. produce a release note summarizing:
   - product-visible changes
   - known limitations
   - environment assumptions

If you want downloadable engineering artifacts, package:

- build logs or validation receipts
- a versioned env example
- optional screenshots or judge/demo references

For artifact-oriented milestones, also preserve:

- sample exported MP3
- sample poster PNG
- sample share HTML
- sample video export where browser support permits

## Stage 3. Deployable app output

Choose one hosting path deliberately.

### Option A. Vercel Pro or equivalent

Use when:

- the GitHub org repo stays private
- you want the simplest Next.js deployment path

Recommended shape:

- keep source in private GitHub
- connect repository to a paid Vercel project
- use preview + production environments

### Option B. Prebuilt Vercel deploy

Use when:

- you want tighter control over build provenance
- you want to decouple source visibility from deployment upload

Recommended shape:

1. run `vercel build`
2. verify the local build result
3. run `vercel deploy --prebuilt`

### Option C. Self-hosted/container deployment

Use when:

- you want source and infrastructure fully under your control
- you need to avoid Vercel plan constraints

Recommended shape:

1. build the Next.js app in CI
2. package a deployable runtime image or Node service artifact
3. deploy to your own container or VM platform

## What to package for different audiences

### For engineers

Package or preserve:

- tagged source
- release notes
- environment contract
- validation receipts
- migration notes if schema or exports changed

### For judges or internal reviewers

Package:

- deployed URL
- short product summary
- known limitations
- demo path
- screenshots or short video if needed

### For end users

Package:

- the hosted app itself
- generated song artifacts:
  - MP3
  - PNG poster
  - share HTML
  - video export (MP4 or WebM)

Do not expose internal engineering docs as if they were end-user deliverables.

## Export artifacts are product surfaces

Murmur's exported files are not incidental by-products. They are part of the
product contract.

That means:

- export regressions should be treated as product regressions
- release notes should mention export behavior changes
- compatibility-affecting export changes deserve explicit review
- sample outputs are worth preserving at milestone boundaries

## Recommended next operational step for Murmur

Given the current repository state, the clearest next step is:

1. keep collaboration in the private GitHub repo
2. add a lightweight CI workflow for `lint` + `build`
3. decide whether deployment should be:
   - Vercel Pro
   - prebuilt Vercel deploy
   - self-hosted
4. create a tagged release process only after deployment path is chosen

## Minimum release checklist

- `main` is green locally
- environment variables are documented
- deployment target is known
- exported user artifacts still work
- release note states what changed and what remains provisional

## Suggested next decision

The next explicit team decision should be:

- **deploy path decision**: `vercel-pro`, `vercel-prebuilt`, or `self-hosted`

Until that decision is made, continue treating deployment as an open
infrastructure choice and keep the repository focused on build correctness and
artifact stability.
