01

Landing & First Encounter

The home route (/) drops users directly into HumScreen — no landing page, no explanation, just an orb.

No value proposition for new visitors Critical

The entry page is the recording screen itself. A first-time visitor sees rotating serif headlines ("哼一句脑海里的旋律") and a white orb — but no explanation of what Murmur does, what will happen after they hum, or what the output looks like. The onboarding overlay (HumOnboardingOverlay) is a thin 3-step tooltip, not a value showcase.

Recommendation: Before the orb, show one sample output — a 4-second looping video of a finished song card with its gradient and wave animation. "You hum, we make this." The demo fallback (transcribeAndGenerate(undefined)) already exists; surface it as a visible "Try the demo" button, not buried in error recovery.

HumScreen.tsx:296–305, hum-onboarding.tsx
Demo path is only discoverable through error Notable

The "试听 Demo" button only appears as a secondary action on error cards (inaudible, mic unavailable, etc.). A user who wants to see the product before committing their voice has no way to discover it from the idle state. The demo flow is fully functional (/vibe?demo=1), but hidden.

Recommendation: Add a small "先看看效果" text link below the orb in idle state. This removes the activation barrier for cautious users and lets judges evaluate the product without a microphone.

HumScreen.tsx:890–900 (handleRecoveryAction), VibePage searchParams
Idle headline rotation is disorienting Polish

Five headlines rotate every 9 seconds with a fade. On a first visit, the user reads one, then it vanishes before they've decided to act. The rotation creates movement but doesn't add information — each headline says roughly the same thing in different words.

Recommendation: Show one strong headline on first visit. Only rotate after the user has completed at least one creation (localStorage flag already exists for onboarding).

HumScreen.tsx:296–305, IDLE_ROTATE_INTERVAL = 9000
SEO meta is Chinese-only but keywords are bilingual Polish

The OG description is "哼一句脑海里的旋律，MURMUR 帮它长成一首小歌。" — pure Chinese. But the general description is bilingual. Social previews for English-speaking audiences will show Chinese text with no English context.

Recommendation: Use the bilingual format from the description field consistently across OG and Twitter cards.

layout.tsx:66–67 vs 44–45
02

Humming & Recording

Tap the orb → mic permission → record → transcribe → navigate to /vibe.

Mic denial error card doesn't guide to browser settings Critical

When a user denies mic permission, startRecording catches the error and shows a "mic unavailable" card. But the card's text (hum.mic.detail) doesn't tell the user how to re-enable it — on iOS Safari or Chrome, this requires navigating to browser settings, not just tapping "retry."

Recommendation: Detect the denial reason (NotAllowedError vs NotFoundError). For denial: show platform-specific instructions ("Open Settings → Safari → Microphone"). For not-found: show "No microphone detected — try from a device with a mic."

HumScreen.tsx:738–837
No visual hint about recording duration expectations Notable

The timer shows elapsed/limit (e.g. "3.2s / 30s") but there's no guidance about the minimum useful duration. Users who tap quickly after 2 seconds get a "too short" or "inaudible" error. The system trims and validates, but the UI doesn't communicate "hum for at least 5 seconds."

Recommendation: Show a gentle "keep going..." state in the first ~4 seconds. The inputLevelLabelKey system already tracks "quiet" vs "heard" — extend it with a "warming up" phase that discourages early stops.

HumScreen.tsx:1033–1038, recording-progress.ts
Processing messages rotate too fast Notable

During transcription+generation, processing messages rotate every 900ms (tickMessages). This is too fast to read — "Listening to your melody..." → "Polishing the notes..." → "Adding drums..." → "Three vibes brewing..." cycles through in 3.6 seconds total. The user can't absorb what's happening.

Recommendation: Slow to 2.5–3s per message. Better yet, map messages to actual pipeline stages instead of a fixed timer — show "Polishing" when transcription completes, "Brewing" when generation starts.

HumScreen.tsx:478–489, msgTimerRef interval = 900
Audio-reactive aurora is beautiful but unexplained Idea

The blob animation driven by amplitudeSpring is a standout visual — it responds to the user's voice in real time. But there's no moment where the UI communicates "I can hear you" beyond a tiny 12px "Heard you" flash that appears for 1 second and disappears. The connection between voice → visual is felt but never named.

Recommendation: When the aurora first responds to voice, show a gentle "I can hear you ✓" near the orb that persists for 2–3s. This confirms the mic is working and the user's hum is being captured.

HumScreen.tsx:267–280 (amplitudeSpring), 1041–1065 (heard/quiet messages)
Guest gate timing is confusing Polish

Guests can create some songs for free (local note system), but the login wall only appears after tapping the orb when notes are exhausted. The user has committed to recording, mentally prepared their hum, and then gets blocked. The balance pill in the nav shows remaining notes, but the connection to "you'll be asked to log in" isn't clear.

Recommendation: When a guest is at 0 notes, show the login prompt before they tap the orb — replace the idle headline with a gentle "Sign in to keep creating" message, keeping the demo button available.

HumScreen.tsx:494–503 (passGuestGate), 1347–1388 (login wall)
03

Vibe Discovery & Studio Arrangement

Choose from 3 AI-generated arrangements, then refine in a mixing/editing studio.

Hard refresh on /vibe loses all state Critical

If the user refreshes the page on /vibe, vibeVersions is empty (Zustand store resets), and the screen redirects to / silently. The user's hum, transcription, and all generated versions are lost. No recovery, no warning, no "your session expired" message.

Recommendation: Persist the current draft state to sessionStorage or localStorage so a refresh can recover. The restoredDraftAt mechanism already exists for restored drafts — extend it to handle refresh recovery. At minimum, show a "Your session expired" message instead of a silent redirect.

VibeScreen.tsx:201–205 (redirect guard)
Vibe cards lack auditory preview affordance Notable

The interaction model is "tap = commit, long-press = preview" — but there's no visual hint that long-pressing exists. The play button is small (44px) and positioned at the bottom-right of a large gradient card. Users are more likely to tap-to-commit than discover the preview. Yet preview is the most important action — you shouldn't pick a vibe you haven't heard.

Recommendation: Make the play button more prominent (centered, or auto-play the first card on arrival), and add copy like "Tap ▶ to preview, pick when you're ready." Consider auto-auditioning the first card after a short delay.

VibeScreen.tsx:676–730 (button group), 301–337 (handleAudition)
Iris-close transition delays content by 1.25s Notable

The vibe page plays a dramatic iris-close → rainbow ring → iris-open sequence on arrival. The content is invisible for 1.25 seconds (setTimeout 700ms + 550ms). This is a beautiful cinematic moment the first time, but becomes friction on repeat visits and during demo flows.

Recommendation: Keep the full animation on first arrival from a hum. Skip or shorten it on back-navigation, reroll, and demo entry. Track whether it's the user's first vibe arrival in this session.

VibeScreen.tsx:169–179 (arrival sequence timers)
Studio prompt input discoverability Notable

The Studio has a text prompt interface (AurisPanel) for natural-language edits ("make it faster", "add more bass"). This is a powerful feature, but it's positioned alongside more traditional controls (track mixer, scene grid) without explanation. First-time Studio users may not realize they can type instructions.

Recommendation: Add a placeholder in the prompt input that rotates through example edits: "Try: 'add more drums' or 'make it dreamy'". This teaches the vocabulary while demonstrating capability.

StudioScreen.tsx:188–199 (handlePrompt), auris-panel.tsx
Turntable visual is decorative but non-interactive Polish

The Turntable component in Studio is a visual centerpiece showing the cover art spinning. It's beautiful, but users may try to tap it expecting playback control. The actual play/pause is a separate button.

Recommendation: Make the turntable tappable as a play/pause toggle. The affordance is natural — everyone expects tapping a turntable to play music.

StudioScreen.tsx, turntable.tsx
04

Gallery & Song Detail

Browse saved songs, play them back, view details, and revisit past creations.

Gallery empty state shows demo songs without clear differentiation Notable

When a user has 0 songs, the gallery renders 3 demo songs (DEMO_SONGS) with a small italic hint "这些是示例歌曲 ↓". But the demo songs look identical to real songs — same card component, same gradients, same layout. Clicking a demo song navigates to /song/demo-1 which will show a "not found" state.

Recommendation: Either make demo songs visually distinct (watermark, badge, reduced opacity) or replace them with a single empty-state card: "Your gallery is empty. Hum your first melody →" with a preview of what a filled gallery looks like.

GalleryScreen.tsx:44–87 (DEMO_SONGS), 147–148 (isShowingDemo), 278–290 (demo banner)
Gallery loads all songs in one fetch Polish

The gallery fetches /api/songs and receives the entire list. There's no pagination, infinite scroll, or lazy loading. For power users with 50+ songs, this becomes a performance concern — especially on mobile where rendering 50 gradient cards with artwork images is heavy.

Recommendation: Add cursor-based pagination to the songs API and render the gallery with a virtualised list or "load more" pattern. The sorted memo already handles client-side sorting; move it server-side with the pagination.

GalleryScreen.tsx:118–134 (loadGallerySongsOnce), /api/songs/route.ts
Song detail has no progress bar for audio playback Notable

The song detail page plays MP3 audio via a raw HTMLAudioElement, but only shows a play/pause button. There's no seek bar, no elapsed/total time display, no visual progress indicator. Users can't skip forward, rewind, or see how long the song is before deciding to share it.

Recommendation: Add a minimal progress bar under the turntable/cover art. Show elapsed and total time. Allow tap-to-seek. The durLabel already computes duration — surface it alongside playback.

SongDetailScreen.tsx:208–234 (handlePlay), 412–413 (durLabel computed but use unclear)
Activity heatmap is delightful but context-free Polish

The ActivityHeatmap at the top of the gallery shows creation dates — a GitHub-style contribution graph. It's a nice editorial touch, but there's no label explaining what the colors mean or what the density represents. It also shows empty for new users (no demo data), which feels broken.

Recommendation: Add a subtle tooltip on hover (or tap on mobile) showing the date and count. For new users, show a motivational message instead of an empty heatmap.

GalleryScreen.tsx:237–256, ActivityHeatmap.tsx
05

Export & Sharing

Download audio/video, generate share links, and view shared songs publicly.

Share page has generic, non-personalized OG metadata Critical

When someone shares a song link on social media, the OG preview shows: title = "Shared song", description = "Listen to a song made from a hum in Murmur." There's no song title, no vibe name, no artwork in the social card. This is the single most viral surface of the product, and it's using placeholder copy.

Recommendation: In generateMetadata, fetch the song title and vibe from the database (the function already queries getSongShareMetaByShareCode). Set title: "'{songTitle}' — MURMUR", include the gradient or artwork as the OG image (render a server-side poster), and add og:audio for rich link previews.

s/[shareCode]/page.tsx:19–35 (generateMetadata)
Export options lack format guidance Notable

The song detail offers audio download, video export, and link sharing — but doesn't explain what each produces. "Download audio" could be MP3 or WAV (the code checks audioSrc.startsWith("data:audio/wav")). "Export video" doesn't indicate the format (MP4 vs WebM), resolution, or estimated file size. Users don't know what they're getting until after the export completes.

Recommendation: Show the format and approximate size next to each export button: "MP3 · ~2 MB" or "MP4 video · ~8 MB". The data is available at export time.

SongDetailScreen.tsx:252–277 (exportAudio), 279–299 (exportVideo)
Video export has no progress indicator Polish

exportSongAsVideo is an async operation that can take several seconds (canvas rendering + encoding). During this time, the button shows a busy state, but there's no progress bar or percentage. The user doesn't know if it's 10% or 90% done.

Recommendation: Pass a progress callback to exportSongAsVideo and show a determinate progress bar. Even a fake-but-honest "Rendering frames... Encoding audio..." two-stage indicator would help.

export-video.ts, SongDetailScreen.tsx:279–299
No "share to Instagram/TikTok" optimized format Idea

The video export is a general-purpose MP4/WebM. For the target audience (music creators, young users), a 9:16 vertical video optimized for Instagram Stories/Reels or TikTok would be the highest-impact export. The visual canvas already renders beautifully — just needs a portrait viewport.

Recommendation: Add a "Story format" export option that renders 1080×1920 vertical video with the song title and a "Made with Murmur" watermark. This is a growth lever.

export-video.ts

Auth, Billing & Account

Login, top-up notes, manage profile, handle payments.

Topup page has no pricing comparison or "what do notes buy?" Critical

The topup screen shows three SKU tiers (Starter/Creator/Patron) with note counts and prices, but never explains what a note is worth. "30 notes" is meaningless without context: How many songs does that make? How many hums + generations = 1 note? The COST constant exists (@murmur/core), but it's not surfaced to the user.

Recommendation: Add a conversion line under each SKU: "≈ 10 songs" (based on COST.hum). Also add a brief explainer at the top: "1 note = 1 hum → song creation."

TopupScreen.tsx:79+, COST from @murmur/core
Auth error page is minimal Notable

The /auth/error route exists but likely shows a generic error without specific guidance on what went wrong or how to retry. OAuth failures (Google callback issues, session timeouts) need distinct copy — "Your login session expired, tap to try again" vs "Google couldn't verify your account."

Recommendation: Parse the error query parameter and show specific recovery guidance per error type. Include a "try again" button that clears state and re-initiates auth.

auth/error/page.tsx
Me page loads song count by fetching all songs Polish

The profile page (MeScreen) fetches /api/songs and counts data.length just to display a single number. This fetches all song data (with arrangement states, visual configs, etc.) only to count them.

Recommendation: Add a /api/songs?view=count endpoint or a /api/user/stats that returns just the count. This is especially wasteful on the profile page which doesn't display song cards.

MeScreen.tsx:56–73 (loadSongCount)
No onboarding for payment methods in different regions Idea

The topup page handles USD/CNY currencies and Card/WeChat Pay methods, with auto-detection via useRegionalSkus. But there's no explanation of why certain options appear — a Chinese user sees WeChat Pay, a US user sees Card only. If geo-detection is wrong, the user may not realize they can toggle currencies manually.

Recommendation: Make the currency toggle more prominent and label it clearly: "Paying from China? Switch to ¥ CNY for WeChat Pay."

TopupScreen.tsx:87–113

Global Experience & Infrastructure

Navigation, mobile responsiveness, performance, error boundaries, notifications.

Mobile bottom nav's "journey rail" metaphor is ambiguous Notable

The bottom navigation shows steps in the creation flow (Hum → Vibe → Studio → Gallery) with soundwave bridges between them. This is creative, but it behaves as both a progress indicator and a navigation bar. Steps that aren't "unlocked" yet are dimmed but still visible, and the soundwave bridges imply a linear flow. Users who want to jump directly to Gallery may hesitate because the rail suggests they need to go through Hum first.

Recommendation: Keep the rail for creation flow (when a draft is active), but show a simpler tab bar (Create / Gallery / Me) when no draft exists. The getRecoverableCreationRoute function already tracks whether a draft is in progress.

bottom-nav.tsx:46–56 (visibleSteps), nav-items.ts (MOBILE_JOURNEY_STEPS)
Desktop sidebar vs mobile nav have divergent information architecture Notable

Desktop shows a SideNavWithModal (232px wide, always visible), while mobile shows the bottom journey rail + a separate MobileTopBar. The sidebar likely has links to /me sub-pages (settings, payments, privacy) that aren't in the mobile rail at all. A mobile user would need to find /me first, then navigate to sub-pages — but /me isn't a visible step in the journey rail.

Recommendation: Ensure /me (profile) is always accessible from the mobile rail, even during creation flow. Add it as a persistent icon (avatar) at the end of the rail.

layout.tsx:143–158, side-nav.tsx, bottom-nav.tsx
All screens use 'use client' — no streaming SSR benefits Polish

Every screen component (HumScreen, VibeScreen, GalleryScreen, StudioScreen, SongDetailScreen, MeScreen, TopupScreen) is a client component loaded via dynamic() or direct import. The route pages themselves are mostly server components but they render nothing — just the dynamic client import. This means no server-side content streaming, no progressive enhancement, and a blank page until JS loads.

Recommendation: For content-heavy pages (Gallery, Song Detail, Me), render a server-side shell with static content (headers, metadata, skeleton) that hydrates client-side. This improves perceived load time and SEO. The gallery could SSR the first 6 song cards.

gallery/page.tsx, song/[id]/page.tsx, me/page.tsx
GlobalLoadingIndicator is the only loading state everywhere Polish

Every route and dynamic import uses <GlobalLoadingIndicator /> as the fallback. This means navigating between pages always shows the same generic spinner, regardless of context. The loading state doesn't tell the user what's loading or how long it might take.

Recommendation: Use context-specific skeleton screens: Gallery should show a grid of placeholder cards; Song Detail should show a cover art placeholder with blurred gradient; Studio should show the layout shell with greyed-out controls.

GlobalLoadingIndicator used in page.tsx, vibe/page.tsx, gallery/page.tsx, etc.
No offline or poor-connectivity handling Idea

A manifest.json exists (PWA intent), but there's no service worker registration visible, no offline fallback page, and no network-state UI. If a user is on a train (common mobile music use case) and loses connectivity mid-recording, the transcription will fail silently and the error card will show "unavailable."

Recommendation: Add a network status indicator that warns users before they start recording: "You're offline — recording won't work until you're back online." Cache the Gallery page for offline browsing of saved songs.

layout.tsx:61 (manifest reference), no service worker found
No undo in Studio Idea

Studio edits (track mixer changes, scene selections, prompt edits) modify the version in-place via bumpVersionEditState. There's no undo stack — once a user makes a change they don't like, the only recovery is to go back to vibe selection (losing all edits) or manually reverse the change.

Recommendation: Implement a simple undo stack (last 10 version snapshots). The version object is already immutable-style (spread into new objects), so storing previous snapshots is cheap. Add a visible "Undo" button near the prompt input.

StudioScreen.tsx:140–158 (applyTokens, version mutation)
Background color is warm cream everywhere Idea

Every page uses bg-[#F5F1EB] — a warm cream. This is the brand identity, but the Vibe and Studio pages could benefit from a darker, more immersive background that lets the gradients and audio visualizations pop. The vibe cards' dark gradients against cream create a visual disconnect.

Recommendation: Consider a dark mode for the creation flow (Vibe → Studio) that transitions back to cream for Gallery/Me. The vibe card gradients were designed for dark backgrounds — they'd look stunning on #1A1A1A. The cream works beautifully for the browsing/editorial pages.

VibeScreen.tsx:393, StudioScreen.tsx, layout.tsx:132
