## Murmur v0.6.0 (build 181) — Pre-release

Correctness- and durability-hardening milestone ahead of launch. Where v0.5.0
calibrated the version contract, v0.6.0 makes the money path, the save path, and
the production plumbing fail closed and recoverable.

### Display

- Me screen: `v0.6.0 · 181`
- Developer mode: `v0.6.0 · build 181 · <git-sha>`

### Milestones

- `0.2.0` — core creation loop and music engine v2 foundation
- `0.3.0` — auth, persistence, and deployment readiness
- `0.4.0` — billing, public share, and launch hardening
- `0.5.0` — notification delivery and post-launch polish
- `0.6.0` — billing/correctness hardening, save + generation durability, and
  production topology reconciliation

### Highlights

#### Billing and operation correctness

- **Atomic ZPay grant.** Purchase verification and the note-balance grant happen
  in one transaction so a confirmed payment can no longer succeed at the payment
  provider while failing to credit the account.
- **Operation state machine for transcribe and refund.** Long-running
  operations move through explicit states, so a retried or duplicated request
  reconciles against the existing operation instead of starting a second one.
- **Out-of-order refunds.** Refund and reversal events that arrive before the
  operation they reference no longer strand balance; they are applied
  idempotently once identity is known.
- **No double charge on clip identity.** Generation is keyed by a stable clip
  identity, so a client retry or reconnect does not bill a second note for the
  same clip.
- **Durable generation recovery.** In-flight generations survive a background
  cancel / reconnect and are recovered rather than silently lost or re-billed.

#### Save and generation durability

- **Object-storage audio for new saves.** New-save audio is written to object
  storage when `MURMUR_STORAGE_DRIVER=s3-compatible` and a public URL base are
  configured; otherwise saves fall back to an embedded data URL. Existing songs
  are unaffected.
- **Artifact versioning and provenance.** Saved artifacts carry version and
  provenance metadata so a rendered asset can be traced back to the generation
  that produced it.
- **Draft validation, render-failure states, and API bounds.** Draft payloads
  are validated before persistence, render failures surface as explicit states
  instead of hangs, and save/generation API inputs are bounded.

#### Notifications

- **Delivery completeness.** Broadcasts paginate across every push subscription
  instead of truncating at the first page, so no subscriber is silently skipped.
- **Per-locale daily digest.** The daily digest is assembled per locale.

#### Platform and reliability

- **Auth session-outage precedence.** When the Murmur session store is
  unavailable, requests fall through to a valid Auth.js session instead of
  failing the request outright.
- **Fail-closed DB DSN resolver.** The runtime client, the migration script, and
  Drizzle Kit resolve their connection string through one helper
  (`resolveServerDsn` in `src/lib/db/config.ts`). Runtime prefers the pooled DSN;
  migrations prefer the direct/unpooled DSN. An absent DSN throws instead of
  silently connecting to localhost outside explicit local development.
- **Honest tsc test gate.** Test files are type-checked under a scoped
  `bun:test` types project (`bun run typecheck:tests`) so the test suite can no
  longer hide type regressions behind an untyped gate.
- **Journey navigation scoping.** The journey navigation shell is scoped by
  route so mid-flow screens render the correct navigation.

### Engineering

- Build source of truth: `src/lib/release-metadata.ts`
- Structured log release field: `0.6.0+build.181.<sha>`
- Build number `181` is the latest merged PR number at the previous calibration
  point; bump `APP_BUILD` on the next product release per the rules in
  [../packaging-and-release.md](../packaging-and-release.md).

### Production notes

- Production requires `MURMUR_STORAGE_DRIVER=s3-compatible` plus the S3 bucket
  and public-URL env for object-storage saves; see
  [../repository-operations.md](../repository-operations.md) for the full env
  contract and deploy/migration topology.
- Vercel cron schedules in `vercel.json` must be **daily** on the current plan;
  the billing reconcile/refunds crons run once per day for that reason.
